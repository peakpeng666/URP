# 把研究、推荐、二维面板与现成网上仿真串起来

最新用户范围：主仿真直接复用网上已有项目，路径研究需要考虑跨场景/机器人通用性。自建温室 smoke fixture 只用于可选接口检查，不是默认验收主场景，不继续扩展，也不代表已经选择差速车。上游平台/模型的选型、版本和许可证需独立确认。

## 通用性应放在接口，而不是一个“万能机器人”

建议把公共研究对象限制为实例/任务、约束、访问序列、成本模型及来源；让 scene adapter 提供地图、坐标变换和服务 pose，让 robot adapter 提供 footprint、运动学、动力学限制、导航 action 与遥测转换。统一日志采用显式层级与单位，但保留平台特有字段，不能以统一字段为由丢掉不可行性。

同一研究 route 在不同平台必须重新检查是否适用：差速平台可原地转向，不代表阿克曼车辆可以；点到点访问排序不自动支持覆盖作业；单车闭环不能证明多车避碰/调度；二维平面可行不自动覆盖坡地、机械臂或无人机。上游仿真应分成基准载体组合，而不是用一个温室演示声称通用性。

本包接口可复用但当前不支持：阿克曼最小转弯半径、非完整约束全局规划、覆盖路径、动态障碍规避、多机器人冲突消解、载荷耦合、三维地形或飞行。更换 robot adapter 必须重跑对应约束和负向测试。

## 1. 当前真实的数据链

研究实例与算法运行 → 归档数据/校验器/来源哈希 → 后端已版本化 route API → route-scene v1 → 二维路线展示与 RViz Marker。

这条链上的“线”是任务访问顺序，来自算法及校验器，不是导航系统的可行驶轨迹。单次运行的可行性、最短值、求解器输出、oracle 记录与学习型推荐证据需要分开呈现。每次展示应能回到 experiment、revision、run_id、instance_id 和源 artifact/hash。

route-scene v1 不新增求解器结论，不合并异口径指标，不把 cpu_seconds 当服务时间，也不把 arbitrary_time_units 转成秒。二维面板适合提供任务点/仓库、颜色区分车辆、顺序、未服务节点、距离/约束状态、来源链接；RViz 的价值是让相同展示合同进入未来 ROS 工具链，不是替代面板。

## 2. 推荐系统应该推荐什么

优先明确对象：推荐算法/配置、候选路线、车辆数或时间/质量预算，而不是“看到一条路线就是推荐”。真正推荐至少要保留以下证据：

- 请求上下文和允许使用的实例特征；测试时不可泄漏 oracle 或未来结果。
- 候选方法、资源预算、目标口径、约束和不确定性。
- 推荐策略/模型版本、训练/验证/测试划分与选中原因。
- 可复现的 replay：选中方法执行后实际得到的覆盖、可行性、质量和成本。
- 基线与失败模式：固定默认、简单规则、离线最优 oracle（只作上界，不作为可用推荐能力）。

二维面板可以先把这些字段预留为“未接入”，不能随意构造置信度或合理化推荐原因。后端导出的 recommendation.status='not_available' 应如实显示。

## 3. 机器人属于另一层

算法层决定“按什么顺序做哪些任务”；机器人层决定“在地图中如何安全到达下一个任务点并执行”。中间必须有任务转换层，而不是直连任意坐标到 cmd_vel。

转换层输入至少包括：经过校准的世界/地图、节点到可停靠服务位姿的映射、单位/坐标变换记录、车辆 footprint/动力学、可通行区和障碍物、任务服务规则与失败处理。

后续建议的职责边界：

- 研究后端：可重复运行、指标口径、源证据、推荐决策与实验版本。
- 二维前端：解释与比较任务序列；机器人实测/仿真 telemetry 使用不同图层，不能覆盖算法结果。
- ROS task executive：任务状态机、到达/服务/失败、取消/重试和回传。
- Nav2：米制可导航地图上的规划、控制与行为恢复；不是路线算法的替代品。
- Gazebo：机器人动力学、碰撞与传感器生成；不自动提供正确的任务模型。
- RViz：地图、TF、目标、规划路径、机器人状态、传感器及诊断可视化；不承担物理仿真。

## 4. 建议阶段与硬门槛

### 阶段一：可追溯路线展示（当前云端可做）

完成 scene 合同、二维视觉、revision 与 provenance 展示、异常/无候选/部分服务/重复节点等边界测试。RViz 包做静态和纯逻辑验证，但明确运行未验收。

### 阶段二：复用上游项目的最小机器人闭环（需要获准环境）

选定现成网上项目，固定上游仓库/版本/许可证和官方支持的 ROS/Gazebo 配对，先复现其官方演示并保存环境清单。随后用 robot adapter 接统一任务/反馈与验收记录；出现失败先修环境/官方模型/桥接/适配，不能直接归因于研究算法。

本包自建 smoke 仅在需要隔离排查 bridge 时可选使用，不替代上游官方世界的实际测试。主方案应使用所选项目自己的模型/世界/传感器/launch，不能把一份未经运行的 SDF 宣称为复用了成熟生态。

### 阶段三：有地图的任务导航

优先复用所选上游项目已有的地图、机器人 footprint、传感器、代价地图和导航栈，再接任务执行器；提供绕障、不可达、超时、定位异常、安全停止的负向实验。独立检查 global frame=map、odometry frame=odom、base footprint 与 sensor frame 的连通关系和单位，不把展示用 benchmark_xy 静态接到 map。

### 阶段四：研究路线 → 有效导航任务

以明示合成标定或实际地图创建独立 mapping artifact，保留源 benchmark identity 和 scene revision；建立任务节点到可达服务 pose 的映射、代价矩阵与机器人真实轨迹，比较欧氏序列距离与可行驶距离。遇到不可达应回报任务失败/重规划，不能把直线穿过作物床当成功。

### 阶段五：研究结论与推荐闭环

用机器人仿真观测的路程、时间、能耗代理、任务完成率与失败原因形成新数据集；将 benchmark 结果与机器人结果分层统计。推荐策略在独立测试实例和预算上评估，可视化展示其真正证据与不确定性。

## 5. 实验设计要防止的混淆

- 静态截图不是仿真；轮子转动不一定等于车体移动；有效 topic 不代表数据正确。
- 任务访问顺序、全局导航路径、局部控制轨迹、实测轨迹是四种对象，不应共享一个“route”字段。
- 合成数据演示只证明接口链路，不证明农业场景价值。
- 如果引入物理导航代价，原 benchmark 问题已改变，不能直接拿原最优值当新的真值。
- 推荐训练数据、验证数据和演示数据应显式分开；提供后验最优图只能作为 oracle 对比。
- 时间窗违反可能来自任务规划、导航延误或服务模型，需记录不同层次的时间戳和来源，不能只归因于一个算法。

## 6. 仍待用户/真实场景提供的最少信息

未来进入实际温室模型前需要地图或至少明确尺寸/障碍分布、机器人大小与差速/阿克曼类型、任务节点的物理意义、服务动作/时长、允许的失效模式，以及研究目标究竟是任务排序、方法选择还是完整机器人调度。当前没有这些事实，故不自行假设，也不阻塞已经可做的接口/面板工作。
