# 第二轮：函数补全的开发性静态先导

本方案在看过首轮失败后制定，是开发实验，不是首轮事先注册的确认性测试。首轮原始输出、冻结配置和结果保持不变。仍不执行模型生成的代码，不计算排序正确率或功能 pass@1。

## 固定预算和输入

- 官方模型、修订、权重 SHA256、weights_only、安全加载设置、CPU float32 均沿用首轮
- 两种提示都以 `def sort_numbers(values):` 加 Python docstring 开始：紧凑契约与分项明确约束。语义相同：普通 list[int]（排除 bool）、返回升序新 list、保留重复项、不改变输入、非法类型 TypeError、空列表与负数正常处理；允许 sorted，不展示测试数据或参考实现
- 新配对种子固定为 401、431、463、499、541；每个种子交替运行两种提示，共最多 10 次模型 generate 调用，无贪心追加、无自动重试
- 最大新增 512 tokens，temperature=0.7、top_p=0.95、top_k=0、num_beams=1、batch=1
- CPU 线程改为 1，限制累计 CPU 900 秒、墙钟 1200 秒、地址空间 6 GiB。达到资源上限就终止并报告缺失，不无限重试
- 不根据模型输出修改这两个提示或抽取规则；没有将原 72 例输入或期望答案交给模型，也没有使用动态测试结果调提示

## 原始生成与确定性提取

每个样本保留完整原始提示、continuation、token IDs、停止原因、耗时。先生成全部原文；函数边界提取只作为离线静态后处理，不宣称减少了模型生成 token 成本。

提取规则已在 `src/analyze.py` 固定：

1. 源码必须以指定函数签名开头
2. 用 Python tokenize 的 INDENT/DEDENT 跟踪函数 suite 深度；嵌套函数、字符串和注释不触发函数边界
3. 只有在函数 suite 真正 DEDENT 到顶层后，遇到实际非注释/非换行/非 EOF 的顶层 token，才截取此前原样源码前缀
4. tokenization 在文件结束时自动补出的 DEDENT 不算模型输出的结束边界；仅 EOF 的情况保持原文不变
5. 在观测到边界之前词法失败、缩进错误或有歧义时保持原文并标记无可靠边界；不补引号/括号、不修缩进、不删除函数内部语句
6. 即使边界前的函数内部无效，也保留该内部错误，并在静态分析中记失败；不能挑选后续更好的函数

边界可在后续函数/测试之前出现，后续被截掉的部分可能本身是残缺代码。这正是预先规定的提取效应，必须同时呈现未提取原文，不能冒称整段原始输出已成功。

## 同时报告的指标

每种提示分别报告原文与提取后：AST 可解析数、可编译数、单函数结构数；另报提取边界是否可靠、发生截取数、EOS/长度上限停止、生成错误、未完成尝试。

补充结构诊断：报告去掉起始 docstring 后的函数体语句数，以及是否只剩 docstring。不能把从输入自带 docstring 截出的空实现当成模型完成了实现；这仍不构成功能正确性验证。

每次候选尝试和实际 generate 调用开始前，分别写入并 flush/fsync start 事件；完成后另写 completion 事件。独立外层监督进程记录完整墙钟、用户/系统 CPU 和退出状态，即使内层超时或 CPU 限额终止也保留记录。资源失败不从尝试分母中删除。

这些都是静态语法/结构指标；`compile` 只构造代码对象，不执行它。输入类型检查、排序语义、新对象、不变性等没有动态验收，因此即使静态指标为 100%，也不能称为功能正确。

同一组原文的 raw→extracted 差异主要描述后处理效果；两种提示在相同本轮预算和提取规则下可以做描述性比较。首轮与本轮同时改变提示格式、token 预算、后处理和 CPU 线程，因此跨轮差异不能单独归因于提示优化，也不能比较运行速度当模型性能结论。

## 执行门槛

先完成提取器自检和冻结文件哈希，再经独立审阅确认本方案后开始推理。不得覆盖首轮文件。本轮仍受同一个生成代码沙箱限制，动态执行保持禁止。
