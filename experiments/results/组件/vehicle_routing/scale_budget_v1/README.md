# 新开发实例的规模 × CPU 预算实验

**432/432 次主运行均可行且满足声明的预算；完整重放也为 432/432。成熟求解器的相对排序会随预算变化。**

本轮使用 24 个新开发实例：uniform/clustered × 50/100/200 客户 × 每格 4 个。实例 seeds 2026100500–2026100523，solver seeds 11/29/47。它们不是最终测试集，最终 holdout 没有读取、生成或评测。

## 主要发现

每个实例先平均三个 solver seeds，再对 24 个基础实例等权平均。下降比例的分母是该行指定的比较基线。

| 比较 | CPU 上限 | 主批平均距离下降 | 更好 / 相同 / 更差（基础实例） | 重放平均下降 |
|---|---:|---:|---:|---:|
| PyVRP 相对多起点 VND | 0.25 s | 1.6287% | 20 / 0 / 4 | 1.6357% |
| PyVRP 相对多起点 VND | 1.00 s | 2.2384% | 24 / 0 / 0 | 2.2291% |
| VND 相对 savings | 两个预算分别计算 | 1.3334% | 各 24 / 0 / 0 | 1.3334% |
| PyVRP 的 1.0 s 相对自身 0.25 s | 跨预算 | 0.6171% | 21 / 3 / 0 | 0.6008% |

**四个 uniform n=200 实例是明确的预算反转：**

- 0.25 s 时，PyVRP 比 VND 的距离平均高 0.6238%，四个实例的 seed 均值均较差；重放为高 0.5841%
- 1.00 s 时，PyVRP 平均短 0.4035%，四个实例均更好；重放为短 0.4015%

这是本批新开发数据上的预算依赖排序，不能直接宣布 H1“稳定、可利用的强库互补性”成立。特别是当前 PyVRP 使用默认随机初始化，VND 从 savings 起步；后续需要固定协议的 warm-start 对照，排除初始化配置不足导致的表面互补性。

## 更长计算不一定改善 incumbent

VND 的 **72 个相同 instance/seed 跨预算对，路线和成本全相同**。平均 solver CPU 从 0.2066 s 增至 0.6982 s，确实多探索了动作和起点，却没有在本次设置中超过已保留的最佳解。局部动作总数包括其他起点内部的改进，不能把“多次接受动作”误读成最终 incumbent 持续改善。

这不是算法一般已经饱和的证明，也不能用零收益删除那些额外计算成本。Savings 是构造法，两个预算均提前完成，质量也相同。

## 真实耗时与停止原因

| 方法 | CPU 上限 | 平均 solver CPU | 平均完整子进程 CPU | 平均完整调用 wall |
|---|---:|---:|---:|---:|
| savings | 0.25 s | 0.0100 s | 0.0524 s | 0.0539 s |
| 多起点 VND | 0.25 s | 0.2066 s | 0.2500 s | 0.2516 s |
| PyVRP | 0.25 s | 0.2354 s | 0.3566 s | 0.3584 s |
| savings | 1.00 s | 0.0099 s | 0.0521 s | 0.0535 s |
| 多起点 VND | 1.00 s | 0.6982 s | 0.7416 s | 0.7434 s |
| PyVRP | 1.00 s | 0.9852 s | 1.1042 s | 1.1060 s |

这些是相同可用上限，**不是相同实际消耗**。完整子进程 CPU 和 wall 包含解释器启动、导入和退出；solver CPU 只对应已声明的求解阶段。PyVRP 导入及模型准备费用不会被当作零。

- PyVRP 每个预算的 72 次均在共同 20 ms CPU 返回余量触发停止，未达到 100 万次迭代安全上限
- 0.25 s 的 VND：51 次 CPU 余量停止，21 次完成全部 12 个起点
- 1.00 s 的 VND：40 次 CPU 余量停止，32 次完成全部起点
- VND 未达到 1,000 万次 delta 安全上限；构造法均提前完成
- 主批与重放均没有失败、没有预算不合格输出；因此每个配对统计均保留完整 24 个实例，没有通过删掉困难失败案例制造优势

CPU 余量在 VND 与 PyVRP 上各应用一次，传入的声明 CPU 上限没有缩小。初始化和单次 C++ 操作仍不能由合作式检查抢占，因此协议明确保留所有超额解并列出不合格情况；本批恰好未发生。0.25/1.00 s CPU 对应完整 worker wall 上限 1/3 s，不能把整个进程声称为分别只用了 0.25/1 s。

## 这是一组新配置，不能伪装成只改规模

为让预算真正起作用，本轮 VND work cap 从 10 万升到 1,000 万，PyVRP iteration cap 从 1,000 升到 100 万；VND 仍有 12 个固定类型起点。还给两方法设置了共同 20 ms 返回余量。因此与旧 n=8/20/40 实验相比，规模和运行配置都变了，不能做单因素规模因果归因。这些改动也没有新增算法家族。

采用原 CVRP 合同：未取整欧氏距离、容量精确整数检查、所有客户必服务、n 辆零固定费用同质车，无补给或时长成本。PyVRP 0.14.0 的距离代理为 round-half-up(10^6·distance)，罚项上下界同步缩放；最后仍从原坐标独立评分。

主批及重放的 **288/288 个 PyVRP 输出**均通过独立整数目标求和、原始距离误差界、车队及罚项检查。最大整数代理换算误差为 **1.0883×10^-5** 坐标单位；n=200 的最保守理论界为 0.0002 加浮点余量。该界不是启发式最优性 gap，也不保证代理最优解与原目标完全相同。

- 首次 batch 冻结前，7 个新测试通过：不重复扣余量、构造中断、真正改善后立即中断时保存完整 VND incumbent、PyVRP 第一次回调停止、三种新规模的短预算可行性、上限参数、失败/不合格对的显式排除
- 432/432 保存路线重验一致；JSONL/JSON/CSV、冻结执行顺序、统计重算、源码快照、已安装 PyVRP 哈希、旧实验源码/结果哈希全部通过
- 完整重放 432 次：432 可行且 in-budget，**425 次路线/成本精确相同**；7 次差异均来自 CPU 停止的 PyVRP，0.25 s 有 3 次、1 s 有 4 次
- 7 次差异的完整新旧路线均保留，没有替换主记录或挑选更优版本；各批独立汇总，不把重放当新实例
- 两批都重现四个 uniform n200 实例的预算排序反转；不承诺时间截断下同 seed 严格确定性

原始证据位于 [runs/dev_20261004_01/](runs/dev_20261004_01/)：

## 成本边界

主批 wall **184.963 秒**；父 CPU **3.386 秒**，完整子进程 CPU **184.099 秒**，不重叠 CPU 和 **187.484 秒**。重放另计 wall **185.816 秒**，父 CPU **3.613 秒**，完整子 CPU **184.960 秒**。

两批合计 **864 个进程调用**，wall 约 **370.779 秒**，父加子 CPU 约 **376.057 秒**。独立基础实例仍为 24，不是 864。时钟不包括输入生成/预检/冻结/最终聚合写盘/分析/独立审查及助手、人工和平台费用。这些未计量部分不能声称免费。没有实验侧模型或付费 API。实际运行只验证本云环境，未验证 Ubuntu 22.04。

## 复现

在父目录 `URP/experiments/vehicle_routing`，先按成熟求解器实验的官方来源和 hash 锁安装隔离环境。此目录已有的 24 个 dev 输入不能重生成覆盖。

```bash
.venv-pyvrp-0.14.0/bin/python -m unittest scale_budget_v1.test_scale -v
.venv-pyvrp-0.14.0/bin/python -m scale_budget_v1.experiment run --output scale_budget_v1/runs/my_new_run
.venv-pyvrp-0.14.0/bin/python -m scale_budget_v1.experiment verify --output scale_budget_v1/runs/my_new_run
.venv-pyvrp-0.14.0/bin/python -m scale_budget_v1.analyze_results scale_budget_v1/runs/my_new_run
```

输出和 replay 拒绝覆盖。需保留父目录旧模块/实验的哈希一致文件以执行谱系检查。环境二进制/venv/cache 不随成果包分发。

## 尚不能得出的结论

本轮推进了更大规模与预算敏感性证据。默认初始化差异、只有每格 4 个合成实例、尚未冻结强固定库都限制对互补性的解释。没有实际 selector、完整选择策略净收益、P3/P5 生成成员谱系与费用、最终双轴 holdout、真实农业/机器人约束，H1/H2 仍未完成。
