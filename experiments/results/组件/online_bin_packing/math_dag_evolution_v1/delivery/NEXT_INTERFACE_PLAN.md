# 下一步最小接口验证方案（提议，尚未执行）

## 仅由保存文本得到的诊断

20 个限制停止输出都是不完整 JSON，不能通过截取、补括号或忽略 EOS 合同补记为有效。2 个完整 JSON 各有 16 个节点和 3 个已声明常数，第三个节点均为 `gt(c1,c2)`，两个操作数都是标量；之后还出现 c3 至 c15 等未声明常数引用。这些次级文本问题不替换原先的第一拒绝理由，也没有触发重评。

原提示已要求简短描述、紧凑图和向量条件，但当前模型没有满足。原原生 schema 主要约束 JSON 形状、运算名和数组长度，不编码完整的逐节点类型推导和引用可用性。重复出现同类结构不能单凭外观认定是 schema 转换器错误；当前证据只支持该模型、提示、约束解码和 384-token 预算组合不适配。

## 建议先做独立新版本接口门槛，暂不再做 22 请求研究

最多 3 个请求，保持同一官方模型/运行器和 384 输出 token、ctx2048、2 推理线程、120 秒生命周期、4 GiB AS。选择新种子并在输出前固定全部提示和顺序，无重试：

1. 一个已知手写四节点图的准确转写，只检查紧凑完整输出与类型，不算创造性生成成功
2. 两个真实设计请求，只提供类型化接口和同一个小型合法示例，不提供历史设计/验证序列、适应度或本轮验证分数

新版本可以事前把生成合同收窄为最多 4 节点、最多 3 常数、description 最多 64 字符、紧凑 JSON；解释器与数值合同不变。明确 `cN` 只指实际声明的常数，整数引用指已有节点，`gt` 至少一个向量输入，最终必须是等长有限 float64 向量。示例应逐节点标注类型，并在本地分词器中证明完整示例可在预算内结束。收窄空间必须写为新教学变体，不能据此修改本轮结果。

先离线做标准 schema 正反边界和固定官方 converter 验证。已有简单目标 schema 烟测成功不等于本次更窄合同已经验证。正式新请求仍需新冻结和明确放行。

## 事前成功标准与停止规则

固定转写成功只证明接口转写。两次设计输出必须原文完整、EOS 正常、通过原类型检查；至少一份为非种子图，并在事前固定、与历史面板无关的手写多可行箱微例上产生不同于 FF 与 BF 的选择，才视为进入下一阶段的最低可行证据。另须在声明合法域的预定数值检查中输出有限等长向量。新图身份本身不算新算法，微例行为差异也不算更优装箱策略。

微例与验收条件必须先冻结，失败后不换例、不加 token、不再抽样。若两次设计仍不满足门槛，停止该模型接口路线并报告，不启动新的机制对照。若通过，再设计新的训练/验证研究；本轮已查看验证结果不能被用来选择下一候选或宣称新测试泛化。
