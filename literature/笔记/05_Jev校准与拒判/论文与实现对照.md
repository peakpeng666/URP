## JevOut：P263的可复用攻击测试框架

README.md明确不含实验数据、论文结果、模型权重及proposer微调管线。它是生成/验证/打分框架，不是完整可核验论文数据集，也没有VRP求解算法。已读schema、render、evaluate、metrics、optimize、adaptive、proposer、checker、targets、transfer、CLI、client与相关test_optimize静态正文。

1. **输入→单位→初筛**：cli.py main 75–95从JSONL加载DecisionItem；schema.py DecisionItem.validate_keys_and_boundaries 24–48检查唯一key/gold归属/插入offset，item_to_units 211–246把多gold转每option binary unit。evaluate.py evaluate18–35检查顺序并用selected==gold标clean correct。optimize.py _select_eligible_decision164–197对single要求初始正确、固定非gold target；multi仅clean-correct absent中取P(true)最大者。机械契约不是gold来源正确性的证明
2. **渲染**：render.py derive_boundaries10–25和render_additions32–56按原offset排序追加文本，原字符顺序保留。默认dialogue与passage同样扫描整source句边界，论文BFCL“仅最后user turn”必须靠输入预置boundaries，而非默认实现自动保证（schema.insertion_boundaries与prepare_item链已核）
3. **生成/校验**：proposer.py proposer_input54–86给proposer完整gold/target/private反馈；deterministic_filters89–105检查边界、非空、重复和direct phrase regex。OpenAIContextProposer126–189调用结构生成并cache。checker.py check62–118送原/当前/新句/augmented/question/choices/gold，不含target/概率；check.accepted在schema103–117要求双true双false。checker129–152还有依据reason否决矛盾字段的regex repair，是启发式加强，不是独立语义证明
4. **评分→保留/反馈→停止**：metrics.py target_margin9–22实现epsilon=1e-12 log margin；adaptive.py allocate_parent_indices35–73实现稳定softmax、-50截断、uniform mix和systematic resampling，allocate_with_restarts76–100保留root。optimize_context40–161归档已接受children，下轮按margin采样；_extend_candidate200–339机械→语义→render hash去重→target评估→margin→targeted_flip。完整round后122–127停止，最多particles×rounds accepted调用。失败生成不增target_calls、仍留下attempt记录
5. **代表语境→迁移**：optimize返回best_margin不是紧凑代表；真正transfer.select_representative_attempt15–38优先threshold、少增补、高target概率、早call；transfer_context41–111保持精确源unit/target、destination clean-correct条件并保留源失败fallback；targeted_transfer_rate114–118分母匹配项。已查这一层才判断，不能仅看optimize.best就误称论文紧凑规则缺失

### 可核差异与预算限制
- **one-shot机会数**：论文formal one-shot一次proposal；公开OptimizationConfig.proposal_retries默认1（schema142）、CLI默认1（cli59），_extend_candidate235对所有strategy用retries+1。one-shot只限制1 round/slot（optimize71–72），仍可能两次proposal；要复现formal one-shot需明确retries=0，test_optimize中的one-shot测试也显式设0。这是默认协议差异，非证明论文实际跑错
- **native tie**：P263 PDF16称native selection在距max≤1e-8时保留；targets.py JevTarget._evaluate_payload104–143实际Choice总是119行argmax，native_choice只入metadata140。schema97–99允许1e-8容差不会恢复native选项。影响仅tie/近tie映射，未量化
- **cache版本隔离**：CachedTarget._path199–207只hash target_id/unit/source，未含实际model revision或endpoint；CLI65–72默认target_id=jev。使用同cache跨版本可能复用旧返回（返回result保留model_revision但无check）。论文frozen-lock记录版本是实验声明，公开缓存本身没强制。命中仍计逻辑accepted调用，不是新物理API请求
- **网络与JSON重试**：targets._request_with_retry23–40最多3实际请求；clients.structured_chat30–72遇JSON解析失败可2请求、第二翻倍max_tokens并seed+1，只返回成功那次usage。optimize.proposal_calls=len(attempts)不包含client内部重试；checker丢弃usage（checker95–106）。因此此框架直接统计不足以重建全部物理请求/总成本，不可把accepted call视总费用
- **未覆盖论文分支**：CLI策略仅adaptive/targeted_one_shot/neutral_one_shot，公开OptimizationConfig无label-only/probability-only参数；README排除fine-tuning，故V1/V2和matching ablation数值只能据PDF，无法用供件直接复核。HttpDecisionTarget是generic remote适配器，不是内置OS-Jev/Von/Qwen权重实现

## A. laya：输入到结构输出，温度/拒判与真实成本
核心链 Router._route→load→Agent.system_one/predict_batch→_check_question→_encode_state/common.build_sequence→DecisionModel.forward→_decode_answers→flag_low_confidence。route是显式model/task优先、可选workflow和语言规则，不是按实际任务损失训练的selector。

各问被编码成独立batch row，复用的是state分词，整个batch一次模型调用并不使算量与问题数无关。有限marker/softmax产生Choice、序数期望Score或Noul；同接口不意味与P513单串多answer-slot架构相同。option/head预算可能截相同前缀，marker缺失抛错，相同截断文本另在usage报告；state普通字符串保留前部、conversation list保留尾部。原文P098“512/1024”与现行README可选8192以及长文window方法有版本增量，不能拿新代码改写历史评测。

置信最关键：choice/score的legacy confidence=1-H/logK，answer_confidence=max(p)，Noul为max(p_true,1-p_true)；gate优先answer_confidence。即使注释称calibrated，部署分布仍须实证。predict_long采用max或最自信window，明示输出不是整文校准概率。温度强制[.5,5]且修改时警告未校准；notebook拟合返回[.1,10]，加载可能再改变温度。

训练代码不是P098笼统“Brier”：common.proper_reward是下截log+spherical+序数RPS，notebook同时softCE；固定四epoch/group4/2T4是示例预算。按独立question item保留最多400做temperature calibration，正证是未把同一item训练再校准，局限是一个state的其他question可能仍在训练中。test split另读，当前notebook所有execution_count null/outputs空，存在代码不等已跑结果。log-score截断后注释“严格proper”不可无条件照抄。

冷/热：Router.predict在route/load后重置elapsed起点；工具日志不是完整冷启动墙钟。默认Hub revision不pin，reviewed pin需显式选择；typed reviewed SHA 1a793eb...与P426 bc76315b不同。训练、校准、分词/截窗、短名单、加载、GPU常驻都须总成本记账。

## B. typesafe-router：有边界的示例路由，不是评测系统
API POST读有界body/校验→有key live call或无key mock→createRouter校验候选与fallback→build context/question→wire→normalize→closed set检查→阈值→有效option与日志。默认阈值.75，model低置信回general_model，tool低置信返回clarification且无有效工具ID。invalid选项回退，provider错误明确报错，不伪造mock成功。这些是有用工程正证。

它没有下游执行/权限授权/质量验证/性能标签反馈/预算学习/风险覆盖测量；safe_default是名称不是安全证明。元数据的假定cost/latency不送Jev，不能声称系统优化了这些成本。mock是关键词+softmax(.8)，不能记Jev准确率或校准。normalize clamp每个prob并优先供应商confidence，未校验总和或choice是否argmax，属于协议容错而非概率验证。request timeout20秒围住fetch等待，返回body读取在后；不要把它解释成任意处理硬deadline。

## C. Jev-Mem：真实多关系控制链与评估风险
public API→MemoryBuilder.build（或LoCoMo逐turn）→typing→确定性候选→批量relations→canonical raw node与多视图边→每20写维护；无外传summarizer时只记关系/decision不做新摘要。失败可MAGMA写fallback；精确实体/时间为规则。候选虽top10，find_candidates仍遍历graph.nodes并排序，temporal peers亦全扫，所以“只两次API调用”不保证大规模建图总成本低。

QueryEngine.query在read_enabled走RetrievalController。query→typed need→RRF anchors→stopping→按图分配80预算/beam扩展→四项typed candidate分数加embedding/edge/recency→返回topk→独立SystemTwo answer。预算限次数、节点、边、深度与操作间时延；SDK本身无retry，外层最多max_retries+1并逐attempt消耗budget；LRU cache hit单记次数且usage空。query出错的局部fallback是默认need/相似分数，不能把fallback_to_magma名字理解为每次完整基线重跑。local模型锁等待发生在query预算计时前，metadata单列queue seconds，forward无法硬抢占，故15秒不是全端到端硬限，也不是安全隔离。

## AnyJev adaptive stopping：独立静态复核（追加受托问题）

只审随包代码和文档，不运行任何研究/测试、以下代码根为source/代码参考/AnyJev；供件git commit未给出，完整SHA见文末。本报告不把代码问题登记成PDF页码证据。

## 判定摘要

1. **统计证书条件不足：成立。** 固定门槛下Clopper–Pearson(CP)单侧界实现与其二项式定义相符，但同数据扫描多个门槛选第一个通过者，并不自动继承95%选择后覆盖；batch/running prior又破坏最简单的独立同分布Bernoulli前提。应描述为“同校准样本上的逐门槛CP筛选及若干已报留出实证”，不能无条件称用户未来请求的95%认证
2. **None失败回退与文档不符：静态可证。** threshold=None的失败certificate实际落回默认门槛8.5（或prob .1），不强制全量shift。不是“必然提前停”的运行断言；如果模型margin够高、预算/输入符合adaptive条件则可以早停
3. **校准与部署算法不一致：存在。** calibration record模式强制wave1、全部items跑全部shift；默认部署wave2且early stop导致后续prior只见active hard items；calibration函数还更新running prior。即使修正多重检验，也要认证同一完整推理政策
4. **额外发现的版本漂移：** 当前engine_cost.py命名adaptive的rows没有adaptive_shifts=True，而Decider当前默认False；按现静态路径这些rows不会走adaptive实现。历史表可能来自旧默认，不能据此否定历史测量，宜标供件脚本与既有测量不同版

## A. 固定门槛CP与选择后保证

- anyjev/calibrate/stopping.py cp_upper78–92二分解BinomialCDF(k;n,p)=delta；k>=n返回1，n<=0返回1。固定预先选定策略、未来样本与校准样本同分布且错误指示独立时，这可以作为该策略失配率的单侧置信上界
- choose_threshold106–135设reference=winners[:,-1]（120）；默认np.arange(0,20.01,.25)（121–122）共81个预先网格门槛；123–127每个门槛在**同N行**上重新找stop_step并数bad，均调用cp_upper(bad,n,delta)，128–133返回第一个bound≤target。没有delta分摊、uniform bound、独立确认样本或正确fixed-sequence程序。记录一个选择后bound≤target只说明筛选条件成立，不构成总体覆盖证明
- stop_step95–103使停止时间随threshold非减，但winners不受单调约束。permutation marginalize48–66是每prefix的logmean/mean，前缀argmax可以多次换。纯数学示意（非执行实验）：min_shifts=2；第2/3/4步(margin,winner)分别(1,A),(2,B),(.1,A)，full winner A。门槛.5停2正确、1.5停3错误、2.5跑满正确。故disagreement随门槛既可增又可减；不能用“越保守越安全”的直觉代替同时覆盖/有效检验
- 选择第一个通过者也不是天然alpha-controlled fixed-sequence：该实现可跳过任意多个未通过门槛，然后在较后门槛单次拒绝时宣称通过。有效顺序方法需要它自身适用的预定测试次序和停止/拒绝规则，不能泛借名称
- 更稳妥的未来修复方向（仅建议，未实现）：独立数据选threshold，再对**冻结同版完整政策**在新iid holdout作一次CP确认；或者在明确独立数据/冻结prior前提下对有限81策略做同时界（例如保守delta/81），或另建已证明适用的uniform/序贯risk control。选择后独立验证仍需计全部采样/全shift成本

## C. 校准风险与部署风险不是同一量

1. wave：Decider默认adaptive_wave2（64/165），_run_adaptive_choice701取该值，校准却703强制wave1；choose_threshold.stop_step针对每一个shift。部署只在wave边界721–724判断，可能多读一步或更多。更晚prefix的winner可不同，故“多读一点只会更好”无保证，即使所有prior固定亦然
2. batch dependence：默认prior='batch'（57），prior_for673–688把同次所有active样本的shift_sum与旧running sums合成每shift或pooled position prior；corrected692–697对每样本概率用共同prior除法；contextual.batch_prior36–40与apply_contextual43–47确认共享估计。因此校准行的错误指示共同依赖整批数据，不是未经论证可用的独立Bernoulli计数。对固定none/content_free/frozen独立prior，此具体依赖问题可缩小，但门槛选择问题仍在
3. path dependence：校准record让所有items保留active、全shift；实际部署会移除early-stopped samples（724），后shift的prior按难题子集计算。代码684也明确说明“later shifts see only the hard items”，并做pooled fallback；这不是以全轨迹离线stop_step数bad能自动重放的相同交互系统
4. mutable running state：校准自身在750–753更新self._running；随后部署获得不同历史prior；阈值cert仅记录threshold/stat/question_id与计数等，不绑定wave、prior/running-state、combine/canonical/max_permutations配置。若配置/运行历史改变，证书不会自动作废
5. reference范围：_perms799–804使用self.max_permutations；cyclic_shifts24–27可P<K。choose_threshold里的K=margins.shape[1]实际是读到的P；若调用者限了max_permutations，reference是full-P而非名义所有K选项的full-cycle。应明确声称匹配哪一个参照政策。匹配自家full答案本来也不等于正确率/风险校准
6. output/prior细节：每次decided时和最终输出759–760都调用corrected，若使用pooled fallback，later shifts的总体统计可能改变早停样本最终prior；不能仅证书里的记录时winner当成所有部署最终winner。这里只说明可变计算依赖，未跑构造反例、未量化发生频率

## D. 文档正结果、测试与不可过度推断

- docs/rotation_budget.md7–9给出4模型/任务cell、900states、300校准600heldout；56–61报heldout disagreement .000–.008，保留为**仓库自报有限实证**，不是PDF主证据，也不是复现
- 80–105的engine表明确报告agreement.987，超过1%目标的经验失配.013；文档说“95%允许”，但有限测试集经验率>target本身既不能证明总体风险超标，也不能修复选择后CP覆盖。需要测试不确定性和同policy认证。2.3×–2.7×速度比的run-to-run变动已如实披露，是值得保留的成本证据边界
- tests/test_stopping.py173–199用重复TRUTH状态：STATES是6个key重复6遍（22–26），cal=STATES[:24]*6、held=STATES[24:]（175），是相同6个输入的重复fake数据。它测试工程逻辑，不是独立真实语境统计覆盖；不能把测试名“held_out”当未见源项独立性证据
- bench/layout/margin_default.py per_cell76–101确实先300校准再600评估；但86–92仍同data扫描多个pointwise CP。main133–165还按cells结果选statistic和策略，文档承诺若要跨这些选择给总覆盖仍需额外论证
- **当前engine脚本入口差异**：bench/layout/engine_cost.py decider111–112只转发kw。full115显式False；130–133中的decider(adaptive_wave=w)及138只传wave，都没传adaptive_shifts=True；Decider.__init__62默认False；_run839依赖该flag。所以当前供件称adaptive的rows静态走full非adaptive。历史表/旧默认可以解释，应标“当前公开复现入口与历史协议不一致”，而不是捏造当前运行失败
