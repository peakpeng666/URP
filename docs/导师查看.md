## 课题与已经做成的部分

课题是面向农业机器人任务的路径规划算法库与智能推荐研究。现阶段已有两条应分开的链路：一条是 [CVRPLIB 数值基线](../experiments/baselines/cvrp/README.md)，用于比较容量约束路径算法；另一条是农业工作台，将任务输入、算法建议与求解、独立验算、二维显示、**已适配车型**的 ROS 2 / Gazebo 执行和证据导出串起来。前者的访问顺序或未标定坐标不是米制可行轨迹，也不直接证明农业作业效果。

- 工作台仍使用同一个本机 `http://127.0.0.1:4100/` 入口；首页是农业任务，`#/jobs` 是独立的 CVRP 数值任务，`#/bpp` 是历史装箱资料。操作说明与适用条件见 [setup/README.md](../setup/README.md)。数值任务与农业工作台是不同的执行、记录和验算通路，不应合称一个统一实验。
- 已有 [17 个配置的冻结主计划](../protocol/formal_plan.json)，不是 17 个独立算法家族。正式分母为 **17 配置 × 53 问题 × 5 种子/重复 = 4505 项**；53 问题来自 51 个几何与需求底本，后续划分要把同底本归组。归档重审记录 **4316 项独立验算可行、189 项无有效解**，没有有效解不等于数学上不可行。见 [基线报告](../experiments/baselines/cvrp/results/基线实验报告.md)、[2026-10-17 归档重审](../protocol/audits/20261017/README.md)及 [算法清单](../algorithm_inventory.md)。PyVRP 在本计划内 265/265 可行，是重要的固定强基线；不能由此推出对所有预算或农业任务都最优。
- 主计划、[AILS-II/SISR 的 vendor 120 项](../experiments/baselines/cvrp/evidence/vendor_all120_audit.json)、[接手验收 742 项及旧/新各 48 项](../experiments/baselines/cvrp/handoff/20261016-liyueying/核验与接手.md)各有目的、预算和版本，**不合并分母**，也不拿补做批次填补主计划的统计证明链。

## 智能推荐：原型已运行，收益尚未显示

最新 [冻结模型](../src/lab/models/cvrp-knn-v1.json)所对应的选择器实验是 **train 60 / cal 30 / test 30**，不要与较早 [24 个合成实例的离线 CRC 回放](../src/research/docs/RESEARCH_ACCEPTANCE.md)混写。按 120 条候选成本严格比较，PyVRP 对 OR-Tools 为训练 **51 胜 9 平**、校准 **23 胜 7 平**、测试 **27 胜 3 平**，OR-Tools **0 次严格更优**。这批数据的测试集里 PyVRP 已达到候选池逐例最低成本；当前模型的正常门控流程最终仍选 PyVRP，测试替代选择 0 次、相对固定 PyVRP 的平均收益为 0。它是可运行的学习选择原型与负结果，**不是已证实的智能选择增益**；也不能推断其他分布、预算或候选库永远没有互补性。

实验评估使用每算法 **0.25 秒、两次重复**的特定设置，旧工作台默认求解则是 **3 秒、种子 42**；训练目标为未取整欧氏距离，取整距离输入没有对应的学习策略验证。在 `23fafe4f…` 审查提交上，主推荐面板也未显著呈现全部评估限制；当日是否已补提示看 [交付复核](../setup/2026-10-19/delivery-review/REPORT.md)，演示时仍须说明证据适用域。这不否定工作台可以求解或让人自行比较算法，但不能以 0.25 秒评估为默认 3 秒运行背书。[集成报告的选择器条目](../setup/2026-10-15/integration/REPORT.md)和 [证据哈希清单](../setup/2026-10-15/integration/extended/manifest-sha256.json)指向原始 selector-study；原始包在发布附件而非 Git 树内，仅有模型文件不等于重新复算全部实验。

## 农业与系统证据的边界

- 真实来源的田块轮廓已进入研究，但点位、需求和作业语义多为合成或代理；“访问并停留”不等于采样、喷洒或采摘质量已验证。农业工作台已有实跑闭环，执行目前限定为已适配的同构差速模型；异构、曲率规划能力不等于任意农机可物理执行。见 [工作台说明](../setup/README.md)及 [2026-10-18 规划集成](../setup/2026-10-18/planning-integration/summary.json)。
- 多车物理执行采用保守的整段任务**串行预约**。规划并行 makespan 与包含排队、停车接驳和跟踪的实际工期口径不同，不能相互代替，也不能把串行基线本身叫作错误。Fields2Cover 完整路径修复后，内缩作业区覆盖与全田覆盖须同时标分母；现有示例分别为 **100%** 和 **45.83%**，后者包含合同排除的地头，不能据此说覆盖合同失败。新版完整路线仍缺修复后的物理复验，不能用旧执行记录代替。见 [规划集成原始汇总](../setup/2026-10-18/planning-integration/summary.json)。
- 已有摩擦、合成定位、有界力矩、实际轮关节反馈及故障测试，但它们是未按真实土壤和电机标定的仿真代理。 [地面风险审计](../setup/2026-10-18/ground-risk-audit/summary.json)的 13 场混合正常、压力、故障注入和生命周期用例，**不能把 8 succeeded / 13 写成正常任务成功率**；取消、正确拒绝和清理通过也不等于任务成功。
- [平台快照](../setup/2026-10-18/platform-snapshot/summary.json)镜像基于 `ddb5113e…`，不是上文的 `23fafe4…` 源码提交。容器 warehouse 0/5 与原生同场景 5/5、容器 GUI 限制仍应如实展示。使用镜像启动不能冒充当前源码已全量验收。结果只以当次的提交、依赖、模型、输入和原始日志解释。

主基线的 3604 项并非“无数据”：其中 cloud seed2 的 **901 项**有未 VERIFIED 的 host manifest，本机 seed1/3/4 的 **2703 项**有与结果哈希绑定的 FROZEN resource manifest，缺的是原汇总所引用的主机/环境核验包装；cloud seed0 的 **901 项**具备归档意义的 VERIFIED 链。路线质量、成本和描述性汇总仍可用，已验证同条件耗时配对须降级；原报告也没有跨硬件做速度排名。应优先追回原包装并核验，找不回则保持证据等级，不回填原始记录。详见 [归档重审](../protocol/audits/20261017/README.md)。
