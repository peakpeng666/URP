# URP 部署决策与验收

审查日期：2026-10-14（UTC）／北京时间 2026-10-15。源码基线：`7ae5a75a319bfcbadf15197bb994b788e5500bd2`。

本次审查覆盖静态源码、依赖、官方兼容资料与部署风险，形成部署前决策依据。安装、用户电脑变更、新增测试和正式实验均未执行。

## 1. 决策摘要

建议采用 Ubuntu 22.04 + ROS 2 Humble + Gazebo Fortress + RViz2 + 官方 TurtleBot4 仿真。科研使用独立 Python 3.12 环境，Humble 使用发行版 Python 3.10；入口统一，进程分开管理。安装决定与机器验收尚待完成。

Jazzy/Harmonic 容器是替代候选，不是启动主线前必须再做的一套工程。只有部署前已有可用容器条件，或原生路线出现明确阻碍，才比较变更、恢复成本和最小上游场景证据，并记录一次改选决定。未选中的路线不全量安装，不为统一 Python 直接升级宿主系统。

容器条件不只是 Docker 命令能运行，还包括来源与固定版本、设备授权、显示或无头渲染、通信、数据挂载和容量。使用 NVIDIA 时须有正常宿主驱动及相应 GPU 接入。候选平台只需验证最小上游场景与基本启停，不要求业务 API 或完整调度先实现。所需额外权限应单独处理，不把另一条路线当作绕过拒绝的通道。

环境安装、核心系统、仿真集成和正式研究分阶段建设、分别验收。安装阶段仅检查本阶段所需条件。

## 2. 已知状态与真正的版本限制

已有检查显示：Ubuntu 22.04.5 amd64，约 62 GiB 内存，约 64 GiB 空闲磁盘；Humble ros-base 已装，Gazebo/RViz/Nav2/TB4 尚未安装；uv Python 3.12 已有，系统 Python 为 3.10。Node 24.14 与系统 Node 12 并存。

科研锁定 NumPy 2.5.3、contourpy 1.4.0，要求 Python 至少 3.12；PyVRP 0.14.0 至少 3.11。交付的原生 wheel 与科研恢复入口绑定 CPython 3.12、Linux x86_64。因此当前完整科研依赖不能原封不动搬到 3.10。核心元数据写 >=3.10，不代表全部科研扩展已在 3.10 验收。

Humble 当前 rclpy 为 cp310 二进制，不能直接导入 3.12。科研 runner 用 sys.executable 启动内部 worker，因此应由明确的 3.12 解释器启动整个科研 CLI，不应让 ROS 3.10 导入 runner 再期待子进程自行换版本。

Jazzy 可使两类角色都用 Python 3.12，但不自动统一依赖集合。两个隔离进程以数据协议通信，不要求彼此 NumPy ABI 兼容；分别验证各自实际导入的原生扩展即可。只有同一进程确需混用科研 NumPy 2.x 与 ROS 图像等原生扩展时，才增加对应 ABI 联测。不使用的 cv_bridge 不作为前置门槛。

项目 frontend/package.json 要求 Node >=22.12；现有 nvm Node 24 在声明范围内，系统 Node 12 不满足。尚未实际构建验证。发布时可交预构建静态资源，目标机器不必为浏览页面临时编译前端。

官方支持表当前列 Humble/Fortress 到 2027 年 5 月，Jazzy/Harmonic 到 2029 年 5 月。不能继续沿用 Fortress 2026 年 9 月的旧日期。生命周期：[ROS REP-2000](https://github.com/ros-infrastructure/rep/blob/master/rep-2000.rst)、[Gazebo 发布表](https://gazebosim.org/docs/all/releases/)。

## 3. 分阶段部署门槛

### 软件源与包事务

目前官方 ROS 源与清华镜像同时启用，均为 jammy。后续核对签名、候选版本与来源，确定主来源并保留可恢复配置。默认 Humble/Fortress 优先使用 ROS 仓库，按需添加 OSRF。软件源是否存在问题，需结合上述核对结果判断。

安装前做逐层及全集 APT 模拟事务，记录新装、升级、删除、降级、hold 改变，结合候选包元数据估计下载和解包增量。模拟事务不证明实际下载量、运行峰值或安装成功。出现意外删除、降级、跨发行版包、驱动/内核/桌面变更、签名错误即停止。禁止靠忽略签名、强制降级、全局 autoremove 或 full-upgrade 消解问题。

Humble 默认 ros-gz 与非默认 ros-gzharmonic 存在冲突，不能安装“最新版 Gazebo”替代匹配版本。[Gazebo 官方配对](https://gazebosim.org/docs/fortress/ros_installation/)

### 图形与设备

检查任务中未发现 NVIDIA/DRI 节点，nvidia-smi 无法通信，glxinfo 无法打开显示会话。该上下文的图形验收尚未完成，驱动状态需在宿主会话进一步核对。

后续获准检查时，先比较正常宿主会话与任务上下文，再核对实际设备、加载模块、用户态版本、显示会话与 renderer。RTX 5090 属 Blackwell，NVIDIA 官方要求 open kernel modules，不能只凭 595 版本号判断配置正确。[NVIDIA 同版本说明](https://download.nvidia.com/XFree86/Linux-x86_64/595.99.02/README/kernel_open.html)

不顺手重装驱动、切内核、禁用 Secure Boot、修改设备权限或启用容器 privileged。容器仍依赖正常宿主驱动与适当授权；headless 传感器也可能需要渲染上下文。

### 容量

64 GiB 是当前余量，不是已证明足够的安装预算。分别核算下载缓存、解包净增量、旧包恢复材料、镜像层、构建输出、模型资源、Python/Node 缓存、日志、rosbag、结果和导出副本。

安装前以包元数据、计划资产、恢复材料形成初步预算，并设保留空间与停止线；最小安装后再用短时场景/录包补测运行峰值，超预算停止扩装。不能把尚未安装才可测得的数据反过来设成首次安装前条件。未测项标“待测”，不擅自清理旧数据、内核、镜像或回退包。图形未验收阻止对应能力放行，不阻止不依赖 ROS 的科研核心。

### 恢复

包名清单不等于可恢复；移除元包不会撤销依赖升级。项目/config/锁文件需独立备份并抽测恢复；涉及已有基础包升级时，须有可取得的旧版本依赖闭包或经验证的系统恢复方案。Drive 项目副本不是可启动系统镜像，容器镜像也不包含所有持久卷与宿主配置。

## 4. 比 Python 分开更重要的工程缺口

本次审查所用版本的工程缺口：

1. start.sh 目前不是科研、ROS、仿真的统一启动器，缺分组件就绪与关闭回收。
2. 后端仍以只读展示为主，缺真实计算任务接口、可恢复读取的任务记录、结果导入及可靠取消/重启对账。持久队列只是可能实现，不是唯一方案。
3. 前端 4173、后端 4180 不同源；后端无通用 CORS 并拒绝跨源 POST。需同源托管或受控本机代理，不以全开放 CORS/0.0.0.0 绕过。
4. 当前科研 worker 新建 session；只终止外层 CLI/进程组可能遗留工作进程。产品取消必须确认整个作业所属进程集合停止，禁止按通用进程名误杀其他工作。
5. 当前 CVRPLIB 结果与旧 VRPTW 导入链分离，不能把历史路线图当作新求解结果已接通。
6. CLI 只支持 1/5 秒验收预算，产物标记 acceptance_only；正式批次协议尚未冻结。不能改标签冒充正式研究。
7. 当前机器人桥仅发布 MarkerArray，不执行导航。图示 XY 无真实尺度，route-scene 明确不可直接用于仿真导航。

证据：[启动入口](https://github.com/peakpeng666/URP/blob/7ae5a75a319bfcbadf15197bb994b788e5500bd2/src/start.sh)、[科研 runner](https://github.com/peakpeng666/URP/blob/7ae5a75a319bfcbadf15197bb994b788e5500bd2/src/research/src/urp_research/cvrplib/runner.py)、[CLI](https://github.com/peakpeng666/URP/blob/7ae5a75a319bfcbadf15197bb994b788e5500bd2/src/research/src/urp_research/cvrplib/cli.py)、[仿真现状](https://github.com/peakpeng666/URP/blob/7ae5a75a319bfcbadf15197bb994b788e5500bd2/src/robotics/README.md)。

## 5. 系统接线合同

统一入口管理 API、科研工作进程、独立结果检查、二维展示及可选仿真。各进程用明确解释器、工作目录和最小环境。初版同时只运行一个科研任务，忙时明确拒绝或进入受控队列，不承诺并发；正式计时实验不与重负载仿真争抢 CPU。

最低限度保存任务与尝试身份、输入/算法/参数/代码版本、状态、产物和日志关联。页面刷新不能丢任务；重启后不能将失联任务宣称成功或自动重跑。文件记录或小型本地数据库均可，不为首个闭环强行引入消息中间件、独立调度服务或复杂分布式架构。

幂等键、科研唯一键、attempt 和派生仿真 episode 分别解决重复请求、重复实验、执行尝试与世界重置身份。可用简单存储实现，但语义不能混淆。失败和取消记录保留。

取消流程为：记录请求 → 所有者处理 → 停计算/动作 → 确认进程或动作停止 → 封存终态。HTTP 已受理不等于已停止。重启后先对账，PID 必须结合启动身份与进程归属，避免 PID 重用误判。

求解 deadline 用单调墙钟；仿真轨迹用模拟时钟，但 watchdog 用独立墙钟，避免暂停世界后超时也停止。reset 后建立新 episode，拒绝旧反馈覆盖新任务。

科研 CVRPLIB 成本仍按其整数逐边距离合同；二维访问顺序、导航几何路径、物理执行轨迹分别保存计量。任意 XY 不等于米，点需求不自动等于千克。物理任务必须登记地图、尺度、坐标转换、机器人 footprint、任务服务条件和可达性。

CVRP 输出访问顺序时，Nav2 可负责两点间运动；不能将默认 Nav2 的避障路径声称为项目算法生成。若研究几何规划，须显式接入项目路径，并记录控制器、平滑及每次重规划。[Nav2 Humble 接口](https://github.com/ros-navigation/navigation2/blob/humble/nav2_simple_commander/nav2_simple_commander/robot_navigator.py)

## 6. 分阶段安装与验收

G0：确定本地项目路径、发布快照、依赖及来源、容量、备份与恢复。实际路径仍待确认。

G1 核心闭环：明确 3.12 科研环境 → 同源 API → 单任务执行与持久任务记录 → 一个界面新任务 → 真求解 → 独立检查 → 二维结果 → 导出 → 停止回收。核心不依赖 ROS，可与 G2 并行推进。

G2 上游原样仿真：先 ROS 通信，RViz 图形检查单列；再 Gazebo 空场景/桥接/时钟，再官方 TB4 模型/TF/传感器，再固定地图定位及单目标导航。需要建图才加 SLAM。采用正确发行版启动入口，不照搬跨版本教程或机器人整机配置脚本。[TB4 官方安装](https://turtlebot.github.io/turtlebot4-user-manual/software/turtlebot4_simulator.html)

G3 项目接入：将已明确物理映射的项目输出接入上游环境，记录 action、几何路径、实际轨迹、服务账本、碰撞/越界观测。没有观测的指标写未知，不填零。多车计划在单机器人逐路线执行时如实命名，不能叫同时多机器人协同。

G4 发布与恢复：断网运行已承诺的核心及仿真能力；导出移至新目录后可读、可复核；没有旧绝对路径、外部 CDN 或临时模型下载依赖；完成故障、取消、重启与恢复演练。录像只作历史备份，不冒充当次实时仿真。

G5 正式基线：独立冻结 53 例计划、算法、种子、预算、分层、重试与失败分母。正式批次目前未开始；验收演示不计入正式成绩。P5 跨任务生成独立签收，不以界面或默认导航抵扣。G5/P5 不是开始核心开发或环境安装的前置条件，但已承诺的研究内容仍保留在中期总清单中。

2026-10-19 补充：G5 仍保留 2026-10-14 的待签收状态。后续材料包括 `experiments/baselines/cvrp` 中冻结计划 `cvrplib-17alg-53case-5s-5seed-20261015` 的 4505 项执行与汇总，以及李月莹在 `50b3b2c` 上补做的 742 次调用。后者全部标记 `acceptance_only`，该提交尚无正式计划文件，其种子、算法清单和失败分母也不符合上述冻结方案。验收演示与这份补做均不计入 G5 正式成绩，两份材料本身尚不足以完成 G5 签收。核验记录见 `experiments/baselines/cvrp/handoff/20261016-liyueying/核验与接手.md`。

## 7. 必测反例与成功定义

反例随已启用能力分阶段执行，未安装能力不阻塞核心开发；完整发布覆盖全部承诺能力。至少测试：缺依赖/模型、端口占用、磁盘不足；双击提交、同键异内容、非法参数/路径；超时有候选与无候选；非法路线、假低成本、重复/漏点/超载；求解器崩溃、取消、主进程退出而子进程残留；页面刷新、API 重启、迟到反馈；坐标/单位错误、时钟停滞/回退、目标不可达、Nav2 中断；导出缺件及哈希篡改。

核心通过要求一个新任务贯通 UI、真实科研进程、独立检查、二维结果和导出；仿真集成另要求由结果派生并关联的物理任务实际执行，保存映射、动作和轨迹。两者分别签收，核心通过不替代仿真通过，派生任务不沿用原基准的距离/单位合同。能打开窗口、软件安装退出 0、历史测试数或机器人按默认例程移动均不足以签收。

科研成功、任务完成、导航完成、安全观测和证据完整性分别判定。到达末点不代表所有任务被服务；超时无返回不等于数学无解；未观测碰撞不等于零碰撞。失败按阶段保留，不只汇报成功样本平均。

### 推荐系统不能在系统清单中消失

中期系统应能对支持的任务登记可用算法，输出推荐算法、依据与限制，并允许手动改选；记录推荐策略版本、实例特征及实际执行算法。没有已验证学习器时，可以交付明确标注的规则基线或固定回退，不能称其为已验证的智能推荐成果。

科研上验证推荐有效性时，固定训练/验证/测试划分，按原始实例家族或来源防止变体泄漏。对比固定默认算法及可实现的单一最佳算法基线，按同一计算预算报告质量、失败、推荐开销和 regret；事后逐实例最优仅作参考上界，不能冒充可部署推荐器。若数据不足或尚未训练，标为待验证，不虚构提升。

### 通用性与农业相关性的边界

TurtleBot4 是现成差速移动机器人接线载体，不证明农业机器人运动学或田间可靠性。中期明确覆盖的任务族、约束、机器人模型；不同转弯半径、覆盖任务、地形与多机是后续独立验证维度，不要求此刻装齐平台，也不宣称已经通用。农业分布与 CVRPLIB 的对应需另有数据/文献依据。

### 验收阈值必须预先填写

执行前，在测试单中按场景和研究问题确定导航位置/航向容差、任务服务条件、允许时长、取消确认时限、数据缺失处理、重复次数和资源停止线，运行后保持阈值不变。阈值尚未冻结的运行记为探索试跑，另行安排正式验收。

## 8. 晚些时候部署前的最终决策单

- 默认原生 Humble 主线；只有明确的候选条件或阻碍才记录改选，禁止无期限双线试装。
- 确定本地项目路径和本次执行范围；任何 Codex 启动或续作仍需明确许可。
- 重新核对机器状态、候选包、图形上下文、备份和容量，不能沿用旧预演直接安装。
- 先打通核心和上游原样仿真，再接项目算法；保留分层通过/失败/未验证状态。
- 不夹带 OS 升级、驱动修复、CUDA 全家桶、开机自启或网络开放。
- 源码和依赖锁定后再运行正式批次；保留原始结果、失败证据与交付索引。

本轮修订确定了默认路线，调整了安装前条件和跨进程 ABI 检查范围，以行为验收要求组织系统设计，并分别列出安装、核心、仿真和科研的签收条件，补充推荐与通用性的验证要求。修订直接更新现用文档。
