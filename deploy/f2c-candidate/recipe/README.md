# Guarded Jammy Fields2Cover candidate recipe

Status: **review-ready helper, not a prepared or executed native build**. This directory contains newly written portable Python/Bash only. It contains no Debian package/runtime/host lock, private database, secret, bundled compiler or native binary. The old candidate and application/tests are not modified.

## Scope and runtime acceptance gates

Target: official Fields2Cover 2.1.0, CPython **3.12.13**, Ubuntu **22.04 x86_64**, GCC/G++ **11**, and the exact OR-Tools **9.15.6755** Python wheel as its only OR-Tools runtime provider. The official Jammy C++ archive supplies reviewed headers/interface information only. Its libraries must not enter any build/runtime search path. GDAL30, GEOS, TinyXML2-9, TBB and other declared Jammy system dependencies are not copied into the wheel-provider directories. Explicit zlib linking retains the reviewed wheel-owned `ortools/.libs/libz.so.1` at link time. This does not pin runtime SONAME selection: the sole allowed alternative is the authenticated actual Jammy `libz.so.1`, with both providers required to satisfy version/strong-symbol obligations and exactly one measured provider mapped per tested process. No other duplicate-provider exception is permitted; complete transitive system/wheel closure remains an acceptance gate.

Public source locks, matching Jammy header evidence and independently authenticated Jammy package indexes can support later preparation. Authentication of repository metadata does **not** establish an installed, complete transitive package closure. The implemented package/preparation helpers derive the actual same-runner package resolution, downloaded package closure, exact installed host/Python/loader input trees, CMake interface/provider closure and externally anchored complete manifest during a future authorized run. Those live measurements do not exist yet, and no missing versions or hashes are invented. The static example input template is explicitly incomplete and never substituted for the measured lock. No usable live `artifact-index.json` or `reviewed-inputs.lock.json` is generated by this source-only preparation task.

The frozen boot ID and original host network namespace belong to **one live runner**. A previous job's measured lock is never reused. The reviewed `prepare_live.py` now performs authenticated preparation and programmatic same-job measurement, then immediately hands a measured index digest to the offline builder. Review the immutable preparer/source index **before** launch; no human must inspect a lock inside a short-lived hosted job. This binds measured inputs to reviewed code, not to an assertion that arbitrary newly measured bytes have been manually approved.

## Trust boundary and invocation contract

1. Obtain a separately reviewed copy of this launcher and a trusted system shell and Python. The external index digest must come from the review channel, not be computed from an untrusted bundle immediately before running it. Python and the shell are bootstrap trust roots: a verifier cannot prove an already-compromised interpreter trustworthy from inside that interpreter.
2. Use a fresh caller-owned candidate directory. Its path must be canonical, with no symlink ancestors, whitespace, commas, semicolons or dollar signs. Keep the bundle and host inputs exclusively controlled by the runner account, with no concurrent same-UID writers. This is not a sandbox against malicious root or same-account processes, nor a filesystem snapshot/TOCTOU proof.
3. Start the trusted shell using an empty environment, with profiles/startup hooks disabled. This prevents code in inherited `BASH_ENV`, exported Bash functions or loader variables from running *before* the launcher can clear them. The launcher also removes all inherited exports before starting Python; the actual build constructs a new allowlisted environment and closes inherited nonstandard descriptors in child commands.
4. The launcher verifies the external SHA256 and every indexed helper/manifest byte with inline standard-library code **before importing any candidate helper**. It measures the selected Python and `/usr/bin/bash`, `/usr/bin/env`, `/usr/bin/unshare` before using the namespace launcher. The complete host closure is verified before build writes.
5. `unshare --user --map-root-user --net` is mandatory. The kernel guard compares boot ID and actual namespace identity, checks that only DOWN loopback exists, rejects external routes and inherited socket descriptors, and checks PID1 separation where readable. An environment variable cannot assert isolation. Unsupported unshare is a blocker; no online fallback, container pull or host firewall change exists.
6. Verification checks the exact host/input tree membership, content hashes, permission modes, symlink targets/resolution and locked command aliases. Unsafe paths, special files, candidate hard links, duplicate JSON keys, incomplete scopes, foreign distributions and missing review evidence are rejected. Host scopes explicitly enable alias-aware measurement: regular-file link counts, dangling symlink targets and resolution are captured and compared. Candidate inputs do not get this allowance.
7. Check mode performs no provisioning/build/output writes. Execute mode creates one new `output/` parent with private subdirectories. Existing state, including a dangling symlink, is always rejected. Failed output is preserved; no automatic cleanup/resume/retry exists.

Future invocation, **only after preparation, review and execution authorization**:

```sh
/usr/bin/env -i PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 \
  /usr/bin/bash --noprofile --norc "$CANDIDATE_ROOT/recipe/build_offline.sh" \
  --check-reviewed-inputs --root "$CANDIDATE_ROOT" --python "$TRUSTED_PYTHON" \
  --expected-index-sha256 "$EXTERNALLY_REVIEWED_SHA256"
```

The optional execution mode is `--execute-reviewed-build`, with otherwise identical parameters. Neither command has been run here. Do not use the inner namespace modes or call the builder directly. The verifier's direct `--check` path exists for read-only testing and still requires an external anchor and genuine kernel isolation before a complete preflight can pass.


## Same-job preparation entrypoint

The publication bundle contains pinned `official-source-inputs.json`, `build-requirements.lock`, `recipe/build-wheel-inputs.json`, all executed helper source, and `source-index.json`. The source index has `schema: 1`, `status: reviewed-source`, and a `files` mapping of relative path to `{sha256: ...}`. It excludes itself and the workflow that embeds its externally reviewed digest, avoiding a circular hash. Every executed helper/configuration is included. The immutable workflow verifies this anchor inline before invoking even the APT preparation helper.

After the package helper emits `package-preparation.json` with verified installation and complete relevant transitive archive closure:

```sh
/usr/bin/env -i PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 \
  "$TRUSTED_PYTHON" -I -B "$CANDIDATE_ROOT/recipe/prepare_live.py" \
  --root "$CANDIDATE_ROOT" --python "$TRUSTED_PYTHON" \
  --package-lock "$CANDIDATE_ROOT/package-preparation.json" \
  --expected-source-index-sha256 "$REVIEWED_SOURCE_INDEX_SHA256"
```

The preparer downloads only reviewed HTTPS URLs with pinned size/SHA256, rejects unsafe archive members, extracts headers/CMake metadata but no native library from the C++ archive, checks exact OR-Tools/Protobuf compile definitions, and derives a wheel-only imported target. `readelf` parses native files without executing/loading them. Selected installed commands and all selected system runtime providers must byte-match authenticated package payloads. The full host/input/Python trees and package metadata are then measured and independently rechecked before the index is issued. No Python wheel or source build runs in preparation.

The package module may retain official `pkgconf` for the `pkg-config` root only with an explicit verified provider mapping; unknown removals or generic substitutions are not accepted. Relevant pre-existing dependencies need authenticated package archives too, not merely a transaction delta. Host image tools outside the selected package/provider set remain explicitly measured host inputs; no claim that the entire moving image is a reproducible signed snapshot is made.

Prepare/check/build diagnostics can contain private runner paths. The workflow keeps them local and emits sanitized status/hash/count summaries only. No raw artifact/cache upload is part of this recipe.

## Prepared manifest contract

The externally reviewed same-job preparer creates `reviewed-inputs.lock.json` at candidate root from actual measurements, then an `artifact-index.json` with `schema: 1`, `status: reviewed-complete`, and `files` mapping relative names to `{sha256: <64 lowercase hex>}`. All five executable helpers and the manifest are mandatory. Include any additional material the independent review depends on. The reviewed preparer writes the measured index digest into `prepared-anchor.json`; the workflow passes that value directly to the guarded builder in the same live job. The independent trust anchor is the source-index digest embedded in the reviewed immutable workflow. The template is documentation only and must not be copied as a supposedly complete lock.

A path reference is `{base: candidate|python|system, path: <relative POSIX path>}`. Bases are the selected candidate root, measured canonical Python prefix, and `/`, respectively. `.` is permitted only for the complete Python prefix. No environment expansion, command strings or implicit current-directory lookup occurs.

A locked file row contains:

```json
{
  "ref": {"base": "candidate", "path": "inputs/example"},
  "resolved_ref": {"base": "candidate", "path": "inputs/example"},
  "symlink_target": null,
  "sha256": "REPLACE_WITH_MEASURED_64_HEX_DIGEST"
}
```

This example is deliberately invalid. Absolute host paths belong only in private runner-specific evidence or tokenized host references, not embedded in portable helper code. Archives, wheels and review evidence must be candidate-local. A host command can explicitly record a symlink and its canonical resolved path.

Required sections:

- `review`: six boolean approvals listed in the template, all true only after actual independent review, plus a nonempty list of hashed evidence files. These flags do not themselves prove completeness or ABI compatibility; the external review must support them.
- `host`: exact Ubuntu identity, Python prefix/version/executable file row, actual `/etc/os-release` file row, all commands in `guardlib.REQUIRED_COMMANDS`, nonempty configuration/loader file closure, and exact trees. Fixed required coverage includes the full Python prefix, `/usr/include`, `/usr/lib/gcc`, `/usr/lib/x86_64-linux-gnu`, `/usr/bin`, `/var/lib/dpkg`, plus measured system CMake/pkg-config roots. Include additional relevant host trees/files rather than assuming the minimum list proves every tool dependency.
- Tree rows contain `name`, `ref`, and `entries` from `guardlib.snapshot(path, allowed_root)`. Candidate trees cannot escape the candidate root; host trees use `/` or the Python prefix. Entries include every directory, regular file digest/mode, and symlink target/resolved-relative path/referent digest. **No exclusions are allowed.** `snapshot` is a read-only measurement primitive, not an authorization to freeze changed inputs during compilation.
- `packages`: authenticated Ubuntu22.04 signed metadata file rows, explicit snapshot identity and scope (`immutable-signed-snapshot` or `measured-live-repository`), and the **complete resolved relevant transitive closure**, not just the 13 requested roots. Each resolved row contains `name`, exact `version`, `architecture` (`amd64` or `all`), allowed suite (`jammy`, `jammy-updates` or `jammy-security`), and archive file row. Installed package versions are cross-checked against the already tree-locked dpkg status. Signed metadata authentication and resolver-closure review are separate obligations. A live measured repository is not called bit-reproducible.
- `inputs`: exact named trees in `guardlib.REQUIRED_INPUT_SCOPES`; four source records (`fields2cover`, `steering_functions`, `matplot`, `json`) with archive row, attested `commit`, `source_url`; hash-locked `build_requirements`; complete `build_wheels` file rows. The launcher never resolves or downloads missing inputs. No Debian host locks are reused.
- `interface`: exact official Jammy archive file row and a candidate `cmake_ref` contained by the `ortools-interface` exact tree. Review its imported locations/compile definitions and transitive link interface: every OR-Tools native library must bind to the exact extracted Python wheel, never the C++ archive's library directory. Byte-identical headers are evidence, not a runtime ABI proof.
- `runtime`: exact official wheel file row; `extracted_ref` identical to the `ortools-wheel-extracted` tree root; reviewed system SONAME contract; complete hashed `system_libraries` file rows with system references only. ZIP members are rehashed against extracted files and provider directory layout is checked without importing the wheel.
- `network`: original live host `kernel_boot_id` and `netns`, captured before unshare and reviewed with the rest of the lock.
- `build`: fixed source epoch, two compile jobs, and at least 4 GiB free-disk floor. The runner may require a larger measured budget.

The reviewed preparer sets only preparation-policy/metadata flags after programmatic checks. It never generates a completed native acceptance identity. `interface_metadata_reviewed` means the exact upstream target definitions and the narrow adapter policy were checked, not that structural ABI or numerical behavior is proven.

## Build and acceptance boundary

The future builder uses offline hash-required wheel installation, exact compilers, disconnected FetchContent, disabled package registries and the prior optional Matplot/JSON feature-disable flags. It does not alter upstream `-Werror`, application source, adapters, tests, tolerances or dependency versions. No broad `LD_LIBRARY_PATH` is used.

Installed RUNPATH is derived from the verified extension member directory to `ortools/.libs` and `ortools.libs`, yielding `$ORIGIN/../ortools/.libs;$ORIGIN/../ortools.libs`. Build RUNPATH may contain the measured wheel extraction directory, but installed link-path augmentation is disabled. The new wheel must still contain the expected extension member or the build result is refused. This structural check does **not** inspect final ELF RUNPATH or all transitive providers.

Even successful future compilation returns **built, not accepted**. Static ELF dependency/GLIBC/GLIBCXX/CXXABI review, no absolute final RUNPATH, resolved transitive provider hashes, a separately located clean Jammy install, both native import orders, exactly three unchanged native contract passes with no skips, full application suite, and repeat-build comparison remain required. No helper uploads results, publishes a wheel, updates a runtime manifest, promotes production, or launches GitHub/Codex.

## Tests actually performed

Run only the standard-library guard suite:

```sh
python3 -I -B recipe/tests/test_guards.py
```

The tests use temporary fixtures under the recipe test directory and a read-only refusal check on this deliberately unprepared candidate. They do not install packages, invoke a compiler, launch unshare, load Fields2Cover/OR-Tools native modules, or execute application tests. Synthetic namespace tests are not proof that a future runner supports unshare. Positive synthetic index/tree tests are not proof of an actual complete Jammy lock or native acceptance.

The additional pure/data-only preparation suite is `python3 -I -B recipe/tests/test_live_preparation.py`; it does not call network, APT, dpkg-deb, readelf, native modules or the full live preparer.

The only approved same-SONAME alternative is `libz.so.1`: `runtime-interface.json` records `provider_alternatives` with policy `exactly-one-first-loaded-compatible-provider` and exact `wheel`/`system` file rows. Both must satisfy the observed versioned dependency contract; the system alternative is included in authenticated Ubuntu archive-byte proof and host hashes. The wheel is still pinned at link time, but that does not determine which compatible SONAME provider was already loaded. Each validation process must map exactly one approved provider, never both or a third provider. This exception applies to no other SONAME.
